# Automatic Copilot model routing by task difficulty: research and design

**Research date:** 2026-09-29. **Status:** implementation-ready MVP proposal, not implemented or enabled. This document distinguishes **Source-verified** public product documentation and repository code, **Interpretation** of that evidence, **DSH proposal** for a future plugin-only implementation, and **Unverified** behavior or missing evidence. Product documentation can change; citations are not proof of an algorithm's private internals, real account availability, or a live DSH installation.

## MVP contract and existing ownership

**Source-verified repository behavior:**

- [`src/account-model-source.ts`](../src/account-model-source.ts) supplies bounded, account-scoped `/models` discovery with single-flight, TTL, cooldown and invalidation. [`src/account-model-catalog.ts`](../src/account-model-catalog.ts) normalizes advertised endpoints, policy, input, limits and supported reasoning; it does **not** provide quality, latency, credit price or global health measurements. New model IDs are not implementation tables. [Compatibility acceptance](./model-compatibility-acceptance.md) defines the fail-closed contract.
- [`src/preview-route.ts`](../src/preview-route.ts) registers the managed `github-copilot-preview` route. Its `PreviewAdapter` extends the published `PiAiAdapter` and implements `listModels`, `resolveModel`, `prepareCall`, and `stream`; a request binds an account/model descriptor lease, credential proof and cancellation lifetime. [`src/preview-provider.ts`](../src/preview-provider.ts) delegates protocol serialization/transport to native pi-ai `streamSimple`. No second generic wire, private registry or Core patch is justified.
- [`src/current-provider.ts`](../src/current-provider.ts) reads the initiating Session's effective request-header selection for search; `Agent.options` is only an activation seed. [`src/compaction-pressure.ts`](../src/compaction-pressure.ts) observes a committed, frozen `llm/stream` request and signals only the stock recovery path; [`docs/copilot-compaction.md`](./copilot-compaction.md) forbids transparent model switches during recovery. Hosted search has a distinct provider/selection policy, including its own account-owned candidate choice; see [search routing](./session-search-routing.md).
- Explicit Session selection and durable history remain Core-owned. `session.selectModel` also changes the future global default, so silently calling it to implement per-request Auto would change unrelated Sessions. Historical planner/executor policies are compatibility-only and must not become a new Auto UI or root workflow; see [retired model roles](./dual-model.md).

**DSH proposal — user contract:** offer one zero-config **Auto · Recommended** virtual model only under the plugin-owned `github-copilot-preview` provider. A user selects it once with the ordinary picker. On each new user turn, route to one actual eligible Copilot model for the entire turn and disclose that model and concise, normalized reasons. Do not add required tier or model settings. Internal Fast/Balanced/Strong classes are policy implementation details, **not** three picker entries or GitHub's Efficiency/Balance/Intelligence tiers. Explicit model selection wins. Never intercept a selection on another provider, route across providers/accounts, silently move the global default, or revive the retired planner/executor experience. This document does not claim GitHub's own Auto router is accessible through this plugin.

**DSH proposal — implementation boundary:** keep virtual Auto as the Session selection and resolve its actual model at a plugin-owned pre-dispatch boundary through the published `PreviewAdapter`/`PiAiAdapter` APIs. Feed an immutable, per-turn routing decision to the existing descriptor-bound native transport; do not rewrite frozen Core requests or durable events, modify shared pi catalogs, copy credentials, change history, or switch models mid-turn. The existing lease and entitlement checks still govern each model call. If public APIs cannot preserve this distinction truthfully, defer virtual Auto rather than patch Core or advertise a misleading alias.

## Two-layer effective directory

**DSH proposal:** combine **(1) a versioned built-in benchmark/model policy**, shipped with the plugin and reviewed whenever a supported lineup or the authoritative evidence changes, with **(2) the dynamic authenticated `/models` catalog** refreshed on login, bounded TTL or explicit refresh through the existing account owner. The policy supplies comparative task-class candidates, default reasoning and benchmark provenance; the catalog supplies current account entitlement, protocol, policy and capabilities. Only their intersection forms an immutable effective routing snapshot (`policyVersion`, catalog generation, account/proof generation, eligible descriptors, ordered decisions). A catalog refresh cannot invent quality/cost ranking or infer category from a model name. The benchmark policy does not authorize a model absent from the account catalog or override disabled policy.

The policy can be a reviewed plugin-owned data object, not a replacement for the general account-driven protocol catalog. This **illustrative schema is not a claim that these model IDs or rankings are benchmarked**:

```text
policyVersion: "example-1"
evidence: { source: "DSH benchmark suite", date: "YYYY-MM-DD", suiteVersion: "example" }
classes:
  Fast:     [{ id: "example-fast-primary", effort: "low" }, { id: "example-fast-backup", effort: "low" }]
  Balanced: [{ id: "example-balanced-primary", effort: "medium" }, { id: "example-balanced-backup", effort: "medium" }]
  Strong:   [{ id: "example-strong-primary", effort: "high" }, { id: "example-strong-backup", effort: "high" }]
```

**DSH proposal — selection:** use exact, ordered primary/backup IDs per class with explicit supported default effort, not a name-prefix heuristic. Intersect candidates with the current snapshot; filter for entitlement/picker/server policy, supported endpoint, tool calling, required image input, context/input/output budget and effort. The first fully eligible ID in the chosen class wins. If a class is empty, escalate to the next *capable* class with a disclosed reason; when none survives, fail explicitly rather than calling an arbitrary model. An unknown ID in `/models` with an independently authoritative, current category may be admitted only as a low-priority provisional candidate after reviewed constraints; without that evidence it is excluded from MVP Auto (or reserved for an explicitly approved last-resort policy). It remains usable through ordinary explicit selection if the existing managed route permits it. No marketing-name classification. Cost and latency are not ranked until reliable per-model evidence exists; account credits and estimated tokens are not price facts. Hard requirements never trade away for cost.

Build the new effective snapshot completely, then atomically publish it only for *new* turns. A prepared/running lease retains its captured descriptor/snapshot; do not mutate it under an in-flight request. Credential/entitlement revocation still follows the existing guard and can abort that lease. A new turn must reroute if its sticky ID disappeared or lost eligibility. TTL freshness and policy updates do not prolong a credential proof; stale/failed catalog discovery yields a named unavailability diagnostic, not a guessed fallback.

## Deterministic classification and turn lifecycle

**DSH proposal — zero extra model calls:** deterministic rules use only permitted current-turn/Session metadata. Signals: scope (symbol/file/multifile/repo/multirepo), operation (explain/search/generate/debug/refactor/review/architecture), ambiguity, tool burden, change risk, context pressure, previous structured failure, phase, modality, latency intent, and task drift. Never use language or user identity as difficulty proxies; unknown means uncertain, not easy. High-confidence simple (single-file explanation, no risky edits or many tools) starts **Fast**; high-confidence complex (multirepo root-cause investigation, security-sensitive change or architectural design) starts **Strong**; incomplete/conflicting evidence defaults **Balanced**. Hard escalation triggers include repeated proven failed repair, high-impact multi-file edits, security review, and tool-heavy architectural work. Image/tool/context/effort needs still act as eligibility filters regardless of class.

**Hypothesis for offline calibration, not an MVP accuracy claim:** score `scope 0..20 + operation 0..20 + ambiguity 0..15 + tool burden 0..15 + risk 0..10 + context pressure 0..10 + failed attempts 0..10`, clamped to `0..100`. Candidate cutoffs `<=25 Fast`, `26..60 Balanced`, `>60 Strong` apply **only with sufficient feature confidence**; hard escalation overrides the sum. Example: one-symbol explanation with no tools → Fast; ambiguous file-local debugging → Balanced; repeated test failures and repo-wide refactor → Strong. Exact score/cutoffs, benchmark ordering and effort defaults require evidence before activation; rules must remain inspectable and versioned rather than pretending to reproduce GitHub's private classifier.

Re-evaluate at each **new user turn**, not each tool call, retry or generated chunk. Freeze the actual model across that turn's agent loop and tool orchestration; a subsequent user turn may route differently. Retain the incumbent for prompt-cache continuity when it remains capable and task class is stable. Upgrade immediately on a strong signal or lost eligibility; downgrade only after a sustained simpler-turn signal (illustratively two consecutive turns) and a verified meaningful benefit, with a bounded Session-local hysteresis record. The earlier **10–15% improvement** idea is only an evaluation hypothesis, not a defensible MVP threshold absent comparative cost/quality data. If turn boundaries or cache provenance cannot be reliably captured through public APIs, disable stickiness rather than reusing another Session's model.

**Structured failure escalation:** after an attributable, non-cancellation, non-refusal task failure, the *next* turn has a floor of Balanced after Fast, or Strong after Balanced; Strong stays Strong without looping. Classify only structured outcomes (for example an explicit failed test/build or validated tool failure), not free-text claims, HTTP strings or speculative quality. Keep this state per Session/subagent and account generation; clear it on successful verified recovery or explicit model override. Never replay the failed request automatically, retry indefinitely, reclassify a safety refusal, or treat a provider authentication error as task difficulty. MVP has **no wire-time model fallback**. A future pre-output fallback needs separately proven side-effect safety, bounded candidates and the same account proof; refusal/safety blocks and partially emitted tools are never replayed.

## Subagents and disclosure

**DSH proposal:** when a parent selected virtual Auto, a newly created child should inherit **Auto policy**, not the parent's resolved actual model. Give each child an isolated effective selection, cache/stickiness record and escalation floor; classify its declared type, task prompt, tool set, read-only status, scope, risk and expected output independently. An explicit child model override always wins, including a non-Copilot choice; then no Auto interception occurs. Historical dedicated-role children retain their existing policy.

| Proposed child role / default | Exceptions requiring stronger routing |
| --- | --- |
| Search or bounded test execution → Fast | Broad investigation, opaque failures, privileged tools or high-impact changes → Balanced/Strong |
| Ordinary implementation, research or review → Balanced | Trivial isolated edits may be Fast; security-sensitive review or repeated failures → Strong |
| Root-cause investigation, security analysis or architecture → Strong | Only a clearly bounded, low-risk subtask may be independently downgraded |

These are *default hypotheses*, never proof of role difficulty. Native child creation may inherit a resolved concrete parent model rather than a virtual ID: verify the actual published descriptor, selection and activation contracts before promising this behavior. If an explicit virtual-ID inheritance cannot be shown, do not silently copy the parent's concrete ID or invent a child-selection write; defer child Auto and let native behavior remain. A per-Session cap on concurrent Strong children may later protect cost/latency, but it is not an MVP guarantee without a public scheduling seam.

Disclose **Auto · Recommended → actual provider/model** and concise normalized reasons (such as `complex-task`, `tool-capability`, `sticky-cache`, `account-unavailable`, `escalated-after-test-failure`); expose rejected candidate *categories* and the ordered eligible pre-wire alternatives for diagnostics. Do not leak raw prompt/source, provider bodies, credentials or unverified prices. Attribute native usage to the actual model and report billing credits as unavailable unless a verified per-call receipt exists. The UI/Remote boundary must be proven to support this attribution without rewriting Core history or making an alias look like the responding model.

## Public seams, acceptance and phased implementation

**DSH proposal — modules:** a pure `auto-model-policy` data/validation module owns versioned, benchmark-backed ordered candidates; an `auto-model-snapshot` composer intersects those with an authenticated catalog/entitlement generation; a pure `auto-model-router` classifies features and selects once per turn with Session/child-scoped hysteresis and structured escalation. The managed `PreviewAdapter` is the only route integration, delegating the chosen *real* descriptor to existing `PiAiAdapter`/native transport and preserving request-budget, replay, authorization and cancellation guards. A small public presentation contribution may render attribution only after the Host can supply a strict, credential-free result. No second wire, independent static capability catalog, Core patch, cross-provider router or automatic profile migration.

**Unverified public-API gates:** (1) Does a pre-`resolveModel`/`prepareCall` plugin seam expose the complete user-turn features, turn boundary and effective selection? `prepareCall` can precede final content, and the current adapter expects a real ID. (2) Can a virtual picker model represent heterogeneous context/effort truthfully while Core's committed request, compaction header and actual provider call agree? (3) Which public surface records actual-model attribution without mutating durable history? (4) Does native subagent creation inherit the virtual ID or already-resolved actual ID? (5) Does Auto inline hosted search use the frozen actual Chat model, or does the existing independent account-owned search policy apply? In either case preserve search's initiating Session proof, explicit overrides, capability probe and one-query semantics; never silently change its model halfway through a turn. (6) Are trustworthy per-model temporary-health, price and latency signals available, and what are the Session/child/cache identities across resumption, concurrent turns and account rotation? A missing necessary seam is a named fail-closed boundary, **not** permission to patch Core.

**Golden acceptance cases:** deterministic no-network tests for single-symbol explanation→Fast, ambiguous debug→Balanced, multirepo architectural/security work→Strong, repeated structured failure→next-turn floor, unknown feature→Balanced, sticky incumbent versus escalation/downgrade, and parent Fast/child Strong plus explicit child override. Intersect catalog updates (new/removed IDs, changed entitlement, stale proof, denied policy, atomic publication with an active lease) with tools, image input, effort, output and independent prompt/context caps; no unauthorized choice, name guessing or context inflation. Exercise concurrent Sessions/children, cancellation, refusal, partial output, no wire-time replay, real-ID attribution, native search consistency, untouched explicit non-Copilot provider and unchanged ordinary fixed Copilot selection. Add unchanged published-adapter and exact-Core fixture checks for virtual-ID selection, real request model, child inheritance and compaction transaction ownership. Synthetic checks are not live OAuth, billing or Desktop evidence.

**Follow-on implementation sequence:** (1) prove the public pre-resolution, virtual picker, attribution and subagent contracts in isolated unchanged-Core fixtures; stop/defer unsupported surfaces; (2) establish consented, versioned benchmark policy and evidence/review process, then golden deterministic classifier tests; (3) implement pure snapshot intersection and atomic publication with account/lease invalidation tests; (4) wire one top-level `Auto · Recommended` route through the existing adapter, with no wire fallback and accurate attribution; (5) add child inheritance only when its native contract is proven, plus search/compaction parity; (6) run full package/compatibility gates, reviewed rollout and separate live-account acceptance. Each phase can be a narrow issue/PR; no phase silently enables a later one.

**Evaluation after MVP:** only privacy-reviewed, derived feature/outcome vectors, never raw prompts/source or credentials. Candidate outcomes include test/build and tool success, override, retry/escalation, accepted/reverted changes, latency, tokens and errors; none alone proves quality. Calibrate on held-out tasks before considering numeric utility weights or a constrained contextual bandit, with independent safety/cost/cache regression checks. No live experiment is authorized by this design record.
