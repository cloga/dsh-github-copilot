# Automatic Copilot model routing by task difficulty: research and design

**Research date:** 2026-09-29. **Status:** design proposal, not implemented or enabled. This document distinguishes **Source-verified** public product documentation and repository code, **Interpretation** of that evidence, **DSH proposal** for a future plugin-only implementation, and **Unverified** behavior or missing evidence. Product documentation can change; citations are not proof of an algorithm's private internals, real account availability, or a live DSH installation.

## Existing DSH ownership and candidate seam

**Source-verified repository behavior:**

- [`src/account-model-source.ts`](../src/account-model-source.ts) supplies bounded, account-scoped `/models` discovery with single-flight, TTL, cooldown and invalidation. [`src/account-model-catalog.ts`](../src/account-model-catalog.ts) normalizes advertised endpoints, policy, input, limits and supported reasoning; it does **not** provide quality, latency, credit price or global health measurements. New model IDs are not implementation tables. [Compatibility acceptance](./model-compatibility-acceptance.md) defines the fail-closed contract.
- [`src/preview-route.ts`](../src/preview-route.ts) registers the managed `github-copilot-preview` route. Its `PreviewAdapter` extends the published `PiAiAdapter` and implements `listModels`, `resolveModel`, `prepareCall`, and `stream`; a request binds an account/model descriptor lease, credential proof and cancellation lifetime. [`src/preview-provider.ts`](../src/preview-provider.ts) delegates protocol serialization/transport to native pi-ai `streamSimple`. No second generic wire, private registry or Core patch is justified.
- [`src/current-provider.ts`](../src/current-provider.ts) reads the initiating Session's effective request-header selection for search; `Agent.options` is only an activation seed. [`src/compaction-pressure.ts`](../src/compaction-pressure.ts) observes a committed, frozen `llm/stream` request and signals only the stock recovery path; [`docs/copilot-compaction.md`](./copilot-compaction.md) forbids transparent model switches during recovery. Hosted search has a distinct provider/selection policy, including its own account-owned candidate choice; see [search routing](./session-search-routing.md).
- Explicit Session selection and durable history remain Core-owned. `session.selectModel` also changes the future global default, so silently calling it to implement per-request Auto would change unrelated Sessions. Historical planner/executor policies are compatibility-only and must not become a new Auto UI or root workflow; see [retired model roles](./dual-model.md).

**DSH proposal:** expose a *plugin-owned virtual Auto model* on the managed Copilot route, preserving Auto as the Session's explicit selection and choosing an **actual** account-eligible model once at a plugin-owned, pre-dispatch boundary. Clone/translate only a dispatch-local invocation into the public native adapter; do not mutate a frozen Core request, Session history, shared pi catalog, credential record, other Session, or global default. Bind chosen model, account proof, route and policy generation to that dispatch; no change after native wire starts or mid-turn tool execution.

**Unverified seam / prerequisite:** the current adapter expects a real `model` ID and `prepareCall` can precede the final request content. An Auto alias cannot simply be passed to `PiAiAdapter` or advertised with invented fixed context/effort capabilities. Before implementation, establish which public selection/dispatch seam exposes the complete relevant task features before model resolution, how `resolveModel`/`prepareCall` and Core's committed request agree on the actual route, how virtual metadata is represented truthfully, and where Core can attribute the actual model without history mutation. If the published APIs cannot provide this safely, document the limit and defer virtual Auto or use an explicitly selected, plugin-local alternative. No Core change is a prerequisite.

## Proposed policy, not a reconstructed vendor algorithm

**DSH proposal — hard eligibility first:** enumerate only fresh, account-proven descriptors from the managed route, then require grant entitlement, enabled picker/server policy, advertised supported endpoint, tool and required modality support, requested reasoning compatibility, sufficient independent prompt/combined context and output budget, preview-route availability, and currently known temporary health. A hard requirement never trades away for lower latency or price. Unknown policy/capability and invalid/stale evidence fail closed with a named diagnostic; do not treat missing health telemetry as proof of a healthy or unhealthy provider. Explicit non-Auto user selection overrides routing; do not silently enroll a native or historical dedicated Session.

**DSH proposal — inspectable features:** derive a bounded, deterministic feature vector from permitted request/Session context: scope (symbol, file, multifile, repo, multirepo), operation (explain, search, generate, debug, refactor, review, architecture), ambiguity, tool burden, change risk, context pressure, failed attempts, current workflow phase, required modality, latency intent, and conversation drift. Do not use language or user identity as difficulty proxies. Only record derived categories and source/version of each feature, not raw prompts, code or credentials. Unknown features stay unknown instead of being imputed as easy. This is a proposed taxonomy, **not** an observed DSH classifier or a claim that every feature is visible at the current adapter boundary.

**DSH proposal — illustrative scoring contract:** as a reviewable starting hypothesis, assign `scope 0..20 + operation 0..20 + ambiguity 0..15 + tool burden 0..15 + risk 0..10 + context pressure 0..10 + failed attempts 0..10`, clamped to `0..100`. Treat a repo-wide refactor, repeated failed repair, or tool-dependent architectural task as provisional escalation triggers regardless of the sum; context fit and required capabilities remain *hard filters*, not score boosts. This arithmetic and any easy/medium/hard bands are **proposed for offline calibration only**, not validated thresholds or production routing defaults. Record a versioned, human-reviewable candidate prior for comparative suitability by task class, with provenance and expiry; unknown new models start conservatively/neutral and never inherit rank from marketing names. Keep that prior separate from the account-discovered capability catalog.

**DSH proposal — objectives and stability:** rank surviving models for estimated task quality, cost and latency using tier-specific utility weights: Efficiency favors lower verified cost after capability/quality floors, Balance trades quality/latency/cost, Intelligence favors quality but may still choose a small model for a simple task. Numeric weights require calibration and must be labeled policy versions. In the absence of trustworthy cost or latency facts, do not pretend to optimize those axes or infer price from token estimates/account-credit deltas; use a documented deterministic tie-break, or disable the affected tier. Reconsider on each dispatch, but retain the actual model for cache continuity unless it becomes ineligible, the task class materially drifts, context no longer fits, or estimated improvement passes a provisional **10–15%** threshold. That threshold is a hypothesis requiring measured evaluation; neither Copilot nor DSH supplies it. Retention must key on Session/branch, actual model, account and proof/policy generation, with bounded lifetime and no cross-Session contamination.

**DSH proposal — attribution and failures:** disclose virtual Auto selection, tier, actual model and normalized reason codes, with rejected-candidate categories and the eligible pre-wire fallback chain. Never reveal credentials or raw sensitive provider bodies. Model-specific token/usage and any *verified* charge data must be attributed to the actual model, not the alias; absent billing receipts are reported unavailable. Preserve native errors, replay, compaction and cancellation ownership. The prudent MVP has **no wire-time fallback**. A later fallback may apply only before output or tool side effects, or to a separately proven replay-safe failure category, with a bounded candidate list and the same account proof. Never replay a refusal/safety block, user request, or partially emitted tool work through a second model; never silently move to another provider/account.

## Evaluation gates and open questions

**DSH proposal — golden cases:** run synthetic, deterministic cases for simple explanation, multifile refactor, difficult bug diagnosis after failed attempts, architecture planning, image/tool requirements, large context and independent input/output ceilings, unknown/unentitled models, missing cost data, policy changes, mid-flight credential rotation, concurrent Sessions, cache-stickiness versus task drift, explicit fixed selection, cancellation, partial output, safety refusal and failed metadata discovery. Assert actual model/alias attribution, deterministic reason codes, no global-default/history write, no unauthorized candidate, no replay and unchanged non-Auto requests. Tests against the unchanged published adapter and supported pinned Core fixtures are needed before any rollout; synthetic success is not a live model-call or billing claim.

**DSH proposal — evidence path:** start with privacy-preserving feature/outcome telemetry subject to explicit product privacy review. Candidate outcomes include test/build result, tool success, user override, retry/escalation, accepted versus reverted changes, latency, tokens and classified errors; none alone is ground-truth quality. Evaluate on held-out tasks by tier and task class, measure safety and cache/cost regressions, then calibrate a versioned deterministic policy. Consider a constrained contextual bandit only *after* offline evidence, opt-in constraints and controlled rollback. No raw prompt/source capture or live experiment is authorized by this document.

**Open / unverified implementation questions:** (1) Which *public* pre-resolution seam exposes current prompt, effective selection and workflow phase while keeping Core's durable request consistent with the eventual actual model? (2) Can virtual Auto metadata truthfully represent heterogeneous context/output/reasoning, or must the UI defer/decompose that promise? (3) Which public surface can disclose and persist actual-model attribution without changing Core history ownership? (4) Should hosted search follow the chosen actual Chat model for this operation, or keep its documented independent/initiating-selection policy, and how is the handoff captured? (5) What trustworthy per-model health, price, latency and quality priors exist for this account, and who is authorized to maintain them? (6) What constitutes a Session/cache key across resumed history, subagents, concurrent turns, account rotation and TTL refresh? Until these are answered with public-API tests, this remains research, not a shipped feature or release plan.
